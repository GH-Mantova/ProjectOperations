**What it is.** Security wave A, slice 3. Sign-in codes and portal password-reset links stop being
written to the production log. A new `isProductionRuntime()` (`apps/api/src/config/runtime-env.ts`)
returns true when `NODE_ENV` is `production` or `WEBSITE_SITE_NAME` is a non-empty string - the
App Service marker - and the OTP delivery port is bound by a factory on that: `DisabledOtpDelivery`
in production, the existing `LoggingOtpDelivery` everywhere else. The portal reset path logs only
the user id in production; outside it the full URL is still logged so developers and e2e runs can
complete the flow without a mailer. Seven files, four of them new specs.

**Two operational consequences, recorded because the review recorded none.** Measured on the
branch: there is no email sender anywhere in `apps/api/src` - no nodemailer, no SendGrid, no Azure
Communication Services, no Graph `sendMail` - and `otp-delivery.port.ts` says so itself. So from
the deploy that carries this:

1. **OTP sign-in fails outright in production** rather than merely going quiet. Before this, the
   factory bound `LoggingOtpDelivery` everywhere, so the code reached the log and anyone with log
   access could complete a sign-in. That is the hole this closes, and closing it leaves no
   fallback: `DisabledOtpDelivery` throws.
2. **Portal password reset is a dead end in production.** `requestPasswordReset` still returns the
   generic "if that email is registered, a password reset link has been sent", the token is still
   minted, and nothing sends it. A client-portal user who clicks "forgot password" sees a success
   message and receives no link.

Neither is a defect in this PR and neither was a reason to hold it - both are the hole closing.
Both last until `pr-sec-a2-email-codes-and-reset-links` wires a real sender. Dev, CI and e2e are
unaffected. Marco was told both, in chat and on the PR, before he removed the label.
