**What it is.** F-2c. Form rules were stored twice: five flat columns on `form_rules`
(`sourceFieldKey`, `targetFieldKey`, `operator`, `comparisonValue`, `effect`) and the richer
`definition` JSON tree. This drops the five columns, deletes `FormRuleInputDto` outright, removes
`rules` from `UpsertFormTemplateDto`, removes the legacy `formRule.createMany` write path, and
updates both seeds, the specs and the metadata catalog. `definition` becomes the single store.

**No intent is lost.** Migration `20260804_fv2_formrule_expand` already copied every row's five
columns into `definition`, idempotently, and this PR keeps `definition`.

**Ordering, which was the whole risk.** `deploy.yml` fires on every push to `main` and, in one job,
runs the production migrations, deploys the API, then deploys the web bundle from that same commit.
Four web call sites still posted the retired `rules` payload, and the global ValidationPipe runs
with `forbidNonWhitelisted`, so merging this first would have taken the rules builder, the designer
publish and template creation to 400 at that deploy. The web half therefore landed FIRST, as #2180,
which was safe in that order because `rules` was optional on the old DTO. Verified on `main` before
this merge: zero legacy-rule hits in `FormsPage.tsx`, `FormDesignerPage.tsx`,
`FormRulesBuilderPage.tsx` and `formDesignerState.ts`, with `FORMRULE_LEGACY_PAYLOAD_RETIRED_V1`
present.
