**Finding 1 - "Return to automatic" lost the suggestion and repriced the line.** The UI sends
`travelIndex: null`. The API's index-only path wrote `travelIndex = null` AND
`travelIndexSource = null` (`scope-waste.service.ts:589-597`), then recomputed planning minutes with
`const idx = dto.travelIndex !== null ? dto.travelIndex : 1.0` (`:732-737`). `travelIndex` is in
`PRICING_INPUTS`, so that PATCH re-runs the cost engine: planning minutes feed `deriveCycle` ->
loads per day -> duration -> price. Returning to automatic therefore repriced the line against a
traffic allowance of 1.00 that no route had ever suggested, and left the provenance chip with
nothing to show.

Nothing persists the suggested index, so restoring it means asking the provider again. A reset now
re-resolves the route when the row has a tip and applies the suggestion with source `geoapify`.
Three cases, all deliberate: with a suggestion, it is restored and planning, loads, duration and
price recompute from it; with no suggestion available, the row records source `none` rather than
storing a 1.00 that would later read as a measured figure; with no tip at all, 1.00 stands, because
there is no route and so nothing to restore - and the snapshot is NOT wiped, only a genuine tip
change still clears it.

**Finding 2 - Find Tip overwrote route kilometres with a straight line.** `handleTipChosen` patched
`mapLocationId` (correct - it triggers the server's re-resolve, which writes `dailyKm` with
`dailyKmSource: "derived"`) and then sent a SECOND patch carrying the straight-line round trip.
`scope-waste.service.ts:564-569` marks any `dailyKm` arriving in a DTO as `manual`, so choosing a
tip replaced a route-derived figure with a worse one and labelled the worse one as the estimator's
own. The automatic write is gone; the distance is still offered as a click-to-apply chip, so a
deliberate override survives and is honestly recorded as manual.

**On fuel, stated precisely.** S8g charges fuel on `totalTripKm` (trips x 2 x one-way km), computed
from `travelKm` and capacity, not from `dailyKm`. Finding 2 did not inflate fuel. What it did was
store and display a wrong daily figure with a false provenance - the number an estimator reads off
the line and trusts.
