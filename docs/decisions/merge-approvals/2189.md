**What it is.** Three fixes to the watcher's own supervision, from the measured incident of
2026-09-24 (node pid 42212 -> `start-watcher.ps1` pid 44740 -> wrapper 1724). Three files:
`supervise-watcher.ps1`, its new test file, and `status-sweep.ps1`.

1. **`ADOPT_REQUIRES_NO_WRAPPER_ANCESTOR_V1`.** The adopt branch logged "a watcher node is already
   running and no wrapper was supervising it" without ever checking whether one was. In the
   incident it was wrong: pid 42212 had a full `start-watcher.ps1` ancestor chain. The log asserted
   a fact it had not measured - which is the failure mode DOCTRINE section 7 exists for, in the
   supervisor of the machine that runs the board. Adopt now walks `Win32_Process` ancestry via CIM
   and returns `exit-supervised` when it finds a `start-watcher.ps1` ancestor, naming every PID in
   the log.
2. **`WATCHDOG_LINE_CARRIES_PID_V1`.** Every WATCHDOG line now carries the writing job's PID, so two
   wrappers writing to one log are distinguishable after the fact rather than indistinguishable.
3. **`WRAPPER_COUNT_ANOMALY_V1`.** `status-sweep.ps1` reported two or more wrappers as health.
   It now reports each wrapper's PID and start time when the count exceeds one, and is
   byte-for-byte identical on the normal 0-or-1 paths.

**Fallback discipline, which is the part worth keeping.** A PID parse failure, a CIM throw or a walk
error all fall back to today's adopt behaviour, tagged `:CHECK_FAILED`. A broken probe must not
block a valid adopt - the instrument failing is not evidence of a wrapper.

**Testability.** `Resolve-WatcherExitAction` takes an optional `-AncestryProbe` scriptblock that
defaults to the real helper, so the 193 lines of new tests inject stubs and run with no live CIM.
The CIM I/O is isolated in `Get-WatcherNodeAncestry` rather than scattered through the decision.

**Out of scope, correctly.** The `ensure-watcher` relaunch race is escalated separately rather than
folded in.

**Why this matters beyond its size.** This lane hit the consequence twice in one day: the watcher
exited with code 1 fifty seconds into a build at 07:30:17Z, and the board then produced two PRs from
one arm (#2156 and #2158). A supervisor that cannot tell whether it is supervised is how that
happens quietly.
