## 3. Where a new file goes

| The file is… | It goes… |
|---|---|
| A decision, roadmap/data-model change, or lesson | `sot/` — Station 05 only. Everyone else proposes. |
| A merge approval | `docs/decisions/merge-approvals/<N>.md` — **Marco writes it. No agent.** |
| A new unit of pipeline work | `pr-<slug>-HOLD.md` at the root of `docs/pr-prompts/`, to `PROMPT-SCHEMA.md`. A cloud/chat lane may draft it but may not arm it or move it. |
| Something needing Marco's judgement | `docs/pr-prompts/needs-marco/`, dated, options stated. Retired into `resolved-<date>/`, never deleted. |
| A design proposal or screen spec | `Claude Design/mockups/` + `Claude Design/docs/` — knowing git cannot see it. |
| A one-off script, log, dump, smoke output | `tmp-outputs/`. **Never the repo root.** Assume it will be swept. |
| Working analysis that is not SOT | The matching `docs/` subfolder — `plans/`, `architecture/`, `audits/`, `diagnostics/`, `runbooks/`, `lessons-learned/`. Not the root of `docs/`. |

**Two traps, restated because they are layout facts:**

- 🔴 Never run `git` through the device bridge against `C:\ProjectOperations2\.git` or the watcher
  clone. A cut-short VM-side call leaves a 0-byte `index.lock` with no Windows process, so
  "zero git processes" reads true forever. Seven occurrences; 56 minutes of frozen board on 1 Sep.
- 🔴 Never `git checkout .`, `reset --hard`, `stash pop` or `git clean` in the dev tree — consumed
  prompts come back. Use `git stash drop`, never `pop`.
