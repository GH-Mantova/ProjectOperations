## 1. Motivation and the three shapes being consolidated

### 1.1 Shape-by-shape schema evidence

**`Case`** — `apps/api/prisma/schema.prisma:5966-6011`.
Sequenced number (`CaseNumberSequence`, table `case_number_sequences`, seq name
`CASE-YYYY-NNN`), enum `CaseType` (defect | warranty | rfi | complaint | other), enum
`CaseStatus` (open | in_progress | waiting | resolved | closed), enum `CasePriority`.
Optional links to Client, Job, Project (`onDelete: SetNull`). `raisedById` (required),
`assignedToId` (optional), `dueAt`, `resolvedAt`, `resolution`. Comment thread via
`CaseComment` (`schema.prisma:6013-6024`, `onDelete: Cascade` from Case).
**Close-out is REOPENABLE** — no `closedById`, no immutable close audit. Comments
are not append-only per the SoT movement rule.

**`CorrectiveAction`** — `apps/api/prisma/schema.prisma:2007-2033`.
Optional `submissionId` → `FormSubmission` (`onDelete: SetNull`), free-text
`sourceFieldKey`. String `priority` (default "medium"), string `status` (default "open").
`assignedToId` (optional), `assignedToRole` (free string), `dueAt`. Close-out fields:
`closedAt`, `closedById`, `closeOutNote`, `evidencePath` (single string path).
**Close-out is auditable** — closer + note + evidence captured but there is no ledger
of intermediate state changes (edits overwrite in place).

**`SafetyIncident`** — `apps/api/prisma/schema.prisma:4383-4412`.
Sequenced number (`SafetyIncidentNumberSequence`, seq name `IS-INC###` generated by
`apps/api/src/modules/safety/safety.service.ts:192`). Optional Tender+Project link,
required `reportedById` (`onDelete: default Restrict`). Domain-specific fields:
`incidentDate`, `location`, `incidentType`, `severity`, `description`,
`immediateAction`, `rootCause`, `corrective` (free text, distinct from
`CorrectiveAction` model), `witnesses String[]`, `documentPaths String[]` (multi).
Close-out: `closedAt`, `closedById` (**Restrict-guarded** via reportedBy).

**`HazardObservation`** — `apps/api/prisma/schema.prisma:4414-4441`.
Sequenced number (`HazardNumberSequence`, seq name `IS-HAZ###`,
`safety.service.ts:257`). Same link/reporter shape as SafetyIncident but with
`observationDate`, `hazardType`, `riskLevel` (not severity), `assignedToId`,
`dueDate` (naming diverges from CorrectiveAction's `dueAt` and Case's `dueAt`).
`documentPaths String[]`. Close-out: `closedAt` only (no `closedById` — audit
trail is weaker than SafetyIncident).

**Sequences that must keep issuing under the same numbers post-migration:**
`case_number_sequences`, `safety_incident_number_sequences`,
`hazard_number_sequences` (`schema.prisma:5959, 4443, 4450`).

### 1.2 Overlap that motivates consolidation

Every one of the three has the same abstract shape:
`number · title · type/kind · status · priority/severity/riskLevel · reporter · assignee ·
dueAt · closedAt · description · attachments · comment/thread`.
The differences are:
- Field names diverge (`dueAt` vs `dueDate`, `priority` vs `severity` vs `riskLevel`).
- CorrectiveAction has ONE `evidencePath`, Safety/Hazard have `documentPaths String[]`.
- SafetyIncident has `witnesses`/`rootCause`/`immediateAction` (WHS-mandated).
- Only Case has a first-class comment thread (`CaseComment`).
- Only SafetyIncident has `closedById` (weakest form of immutable close on the other two).
- Sequences differ in format and reset cadence.

Permission families (`apps/api/src/common/permissions/permission-registry.ts:79-105`):

## 3. Target model proposal (single `Issue` engine with `kind` axis)

Marco's ruling is: one engine, `kind` axis. Given the WHS constraints (§9
PENDING-MARCO), the proposal is **"one engine, one table, per-kind child rows
for domain-specific fields, sequence namespaces preserved"**. This is a
schema-forward proposal — Marco reviews §9 before greenlighting code.

### 3.1 Parent table — `Issue`

Shape (Prisma-ish):
```
model Issue {
  id              String       @id @default(cuid())
  number          String       @unique                 // preserves CASE-YYYY-NNN, IS-INC###, IS-HAZ###, plus new CA-###
  kind            IssueKind                             // enum below
  title           String                                // present in all three; CorrectiveAction currently derives from source field
  description     String?
  status          IssueStatus                           // unified enum, see §3.3
  priorityBand    IssuePriority                         // unified enum, see §3.4
  reportedById    String                                // maps to Case.raisedById / SafetyIncident.reportedById / CA.createdBy
  reportedBy      User         @relation("IssueReporter", fields: [reportedById], references: [id], onDelete: Restrict)
  assignedToId    String?
  assignedTo      User?        @relation("IssueAssignee", fields: [assignedToId], references: [id], onDelete: SetNull)
  assignedToRole  String?                               // CorrectiveAction only today; nullable is fine for others
  occurredAt      DateTime?                             // maps to Case.-, SI.incidentDate, HO.observationDate, CA.-
  location        String?                               // Safety/Hazard populate; Case/CA leave null
  dueAt           DateTime?                             // rename HO.dueDate to dueAt at migration time
  clientId        String?
  jobId           String?
  projectId       String?                               // mirrors current Case link set + adds to Safety (currently Tender+Project)
  tenderId        String?                               // preserved for SI/HO backfill
  submissionId    String?                               // preserved for CA backfill (FormSubmission link)
  sourceFieldKey  String?                               // CA only today
  documentPaths   String[]     @default([])             // superset of Safety's array + CA's single evidencePath (migrated to first element)
  closedAt        DateTime?
  closedById      String?                               // NEW for HO/Case (currently missing), preserved for SI/CA
  closedBy        User?        @relation("IssueCloser", fields: [closedById], references: [id], onDelete: SetNull)
  closeOutNote    String?                               // CA only today; nullable for others
  createdAt       DateTime     @default(now())
  updatedAt       DateTime     @updatedAt

  safety          IssueSafety?      @relation                // per-kind child row (SI + HO fields)
  correctiveMeta  IssueCorrective?  @relation                // per-kind child row (CA-specific rules-engine hooks)
  comments        IssueComment[]                             // supersedes CaseComment
  movements       IssueMovement[]                            // NEW — append-only audit trail (see §9)

  @@index([kind, status])
  @@index([assignedToId])
  @@index([dueAt])
  @@index([reportedById])
  @@index([jobId])
  @@index([projectId])
  @@map("issues")
}
```

### 3.2 `IssueKind`

```
enum IssueKind {
  case_defect       // Case.type = defect
  case_warranty     // Case.type = warranty
  case_rfi          // Case.type = rfi
  case_complaint    // Case.type = complaint
  case_other        // Case.type = other
  corrective_action // CorrectiveAction row
  safety_incident   // SafetyIncident row
  hazard            // HazardObservation row
}
```

**Rationale for flattening `CaseType` into `IssueKind`**: Marco's ruling was
"Case … [becomes] ONE issue engine with types". Keeping Case as one kind with a
sub-type field would preserve one indirection; flattening removes it. The
trade-off is more enum values. **PENDING-MARCO in §9 asks whether to flatten
(this proposal) or nest (`kind: case`, `caseType: defect|…`).**

### 3.3 `IssueStatus` (superset with lossless mapping)

Current:
- Case: `open | in_progress | waiting | resolved | closed` (enum).
- CorrectiveAction: `"open"` default, string.
- SafetyIncident: `"open"` default, string.
- HazardObservation: `"open"` default, string.

Proposed:
```
enum IssueStatus { open, in_progress, waiting, resolved, closed }
```
CorrectiveAction/Safety/Hazard rows migrate as string → enum; string values seen
in prod (audit at migration slice time) must map into the five. Any non-matching
value blocks the migration and requires Marco decision.

### 3.4 `IssuePriority` (superset)

Current:
- Case: `low | medium | high | urgent` enum.
- CorrectiveAction: string default `"medium"`.
- SafetyIncident: `severity` string (freeform, `low | medium | high | critical`
  in practice per e2e).
- HazardObservation: `riskLevel` string.

Proposed:
```
enum IssuePriority { low, medium, high, urgent, critical }
```
Note: `critical` added for Safety severity. `severity` and `riskLevel` field
names disappear at the parent level — safety-specific label is preserved in the
child row `IssueSafety.severityLabel` for display.

### 3.5 Per-kind child rows (safety WHS fields, corrective-action rules-engine hooks)

**`IssueSafety` (1:1 optional child)** — carries WHS-mandated fields that only
apply to `safety_incident` + `hazard`:

```
model IssueSafety {
  issueId         String    @id
  issue           Issue     @relation(fields: [issueId], references: [id], onDelete: Cascade)
  incidentType    String?                 // SI only
  hazardType      String?                 // HO only
  severityLabel   String?                 // SI severity display label
  riskLevel       String?                 // HO risk level display label
  immediateAction String?                 // SI + HO
  rootCause       String?                 // SI only
  correctiveText  String?                 // SI only (freeform corrective, distinct from IssueKind.corrective_action row)
  witnesses       String[]  @default([])  // SI only
  @@map("issue_safety")
}
```

**`IssueCorrective` (1:1 optional child)** — CorrectiveAction rules-engine
metadata that only applies to `corrective_action`:

```
model IssueCorrective {
  issueId         String   @id
  issue           Issue    @relation(fields: [issueId], references: [id], onDelete: Cascade)
  triggerRuleKey  String?                 // for the forms-engine rules trail
  @@map("issue_corrective")
}
```

**`IssueComment`** — supersedes `CaseComment`; usable by every kind:

```
model IssueComment {
  id        String   @id @default(cuid())
  issueId   String
  issue     Issue    @relation(fields: [issueId], references: [id], onDelete: Cascade)
  authorId  String
  author    User     @relation(fields: [authorId], references: [id], onDelete: Restrict)
  body      String
  createdAt DateTime @default(now())
  @@index([issueId])
  @@map("issue_comments")
}
```

**`IssueMovement`** — NEW append-only ledger (see §9). Every mutating write in
the service produces one row; edits never overwrite in place at the audit layer.

```
model IssueMovement {
  id         String    @id @default(cuid())
  issueId    String
  issue      Issue     @relation(fields: [issueId], references: [id], onDelete: Cascade)
  kind       IssueMovementKind             // enum: created | field_changed | status_changed | assigned | closed | reopened | commented | attachment_added
  fromValue  Json?                          // nullable, e.g. { status: "open" }
  toValue    Json?                          // e.g. { status: "resolved" }
  actorId    String?
  actor      User?     @relation(fields: [actorId], references: [id], onDelete: SetNull)
  createdAt  DateTime  @default(now())
  @@index([issueId, createdAt])
  @@map("issue_movements")
}
```

This makes `Issue.status`, `Issue.assignedToId`, `Issue.closedAt` etc. a
projection over the movement log (SoT §258-280 requirement for compliance
state). See §9 for the WHS enforcement discussion.

### 3.6 Number sequences preserved

Three sequences continue to issue in their existing format (no renumbering of
in-flight rows):
- `case_number_sequences` → issues with `kind` in `case_*` get `CASE-YYYY-NNN`.
- `safety_incident_number_sequences` → `safety_incident` → `IS-INC###`.
- `hazard_number_sequences` → `hazard` → `IS-HAZ###`.
- NEW: `corrective_action_number_sequences` → `corrective_action` → `CA-YYYY-NNN`.
  (CorrectiveAction currently has no number — introducing one is a UX win and
  costs one migration column. **PENDING-MARCO §9** if he wants the legacy
  numberless behaviour preserved.)

## 4. Data-migration strategy (append-only-safe with rollback)

**Guiding rule:** no destructive schema change in a slice that also changes the
UI. Migrations happen in expand-then-contract phases; each slice declares
`gate_allow: migrations` and a rollback path.

### 4.1 Phase A — expand (add new tables, do not touch old)

Migration `NNNN_issue_engine_expand`:
- Create `issues`, `issue_safety`, `issue_corrective`, `issue_comments`,
  `issue_movements`, `corrective_action_number_sequences`.
- Add enums `IssueKind`, `IssueStatus`, `IssuePriority`, `IssueMovementKind`.
- No data write.
- **Rollback:** drop the new tables (no old data touched).

### 4.2 Phase B — dual-write

Application code writes to BOTH old table and new `issues` table on every
create/update, in the same transaction. Reads still come from the old tables.
- New `IssueService` writes both, exposes read APIs against `Issue` for
  gradual UI cut-over.
- **Rollback:** feature-flag the dual-write path off; the old tables are still
  authoritative.

### 4.3 Phase C — backfill

Migration script `scripts/backfill-issues.ts` copies every existing row from
`cases`, `corrective_actions`, `safety_incidents`, `hazard_observations` into
`issues` + `issue_safety` + `issue_corrective` + `issue_comments`, seeding
`issue_movements` with a single synthetic `kind=created` row per issue (the
historical audit trail before the split is best-effort — Marco signs off on §9
whether "created at import" is sufficient for WHS).
- Idempotent: rerunnable. Uses source `id` as `Issue.id` for stable joins.
- Emits a diff report; run under `--dry-run` first.
- **Rollback:** truncate `issues` (Phase B still dual-writes on new activity).

### 4.4 Phase D — cut-over reads

UI switches to reading `Issue` (SLICES 6–9). Old tables are still written
(Phase B); they now function as legacy shadow copies.
- **Rollback:** flip a feature flag to read from old tables again; no data loss.

### 4.5 Phase E — stop the dual-write

Migration flag disables writes to `cases`, `corrective_actions`,
`safety_incidents`, `hazard_observations`. Old tables become read-only shadow
copies for one release cycle.
- **Rollback:** flip the flag back on; new writes resume on both sides. Any
  writes made to `issues` during the read-only interval are re-projected to the
  legacy tables by a reverse-backfill script (SLICE 10 ships this script even
  though it should not be needed).

### 4.6 Phase F — contract (destructive)

Migration `NNNN_issue_engine_contract` (SLICE 11, ONLY after a full release
cycle of stable Phase E):
- Drop `cases`, `case_comments`, `corrective_actions`, `safety_incidents`,
  `hazard_observations`. Keep the three number-sequence tables (they still
  issue).
- Drop legacy permission codes (`cases.*`, `safety.*`, CA-specific overloads
  of `forms.*`).
- **Rollback:** none — this is why Phase E must be a full release cycle. The
  contract migration is the only irreversible one; every earlier slice has a
  cheap rollback.

## 8. Risks

### 8.1 WHS audit-trail preservation (the biggest risk)
Consolidating SafetyIncident into a shared table risks losing the
regulatory-specific fields (`witnesses`, `rootCause`, `immediateAction`,
`corrective` text) or their write-time validation. The proposal isolates them
in `IssueSafety` (§3.5) and gates safety-close on `issues.close.safety`
(isHighRisk preserved). SoT §258-280 movement rule is honoured via
`IssueMovement`. See §9 PENDING-MARCO — Marco's read on this is the release
gate.

### 8.2 Number-sequence continuity
Three number formats (CASE-YYYY-NNN, IS-INC###, IS-HAZ###) MUST keep issuing
without collision or reset. Plan preserves the three legacy sequence tables
and only ADDS a new `corrective_action_number_sequences`. Migration Phase C
uses source `id` as `Issue.id` to keep every incoming external reference
(SharePoint folder names, printed dockets, email subject lines) resolvable.

### 8.3 Dual-write drift
Between Phase B and Phase E, two truths coexist. Mitigation: SLICE 6
`scripts/backfill-issues.ts` doubles as a nightly reconciliation check —
`--verify` mode diffs old vs new and pages if a divergence appears.

### 8.4 Comment thread migration
`CaseComment` migrates to `IssueComment`. Existing comments are copied at
Phase C. The `IssueMovement` log for pre-existing comments backfills with a
synthetic `kind=commented` movement (best-effort actor/timestamp from the
`CaseComment` row). Historic edit history is not synthesized (there was none
to lose).

### 8.5 CorrectiveAction has one evidencePath, Safety has documentPaths[]
Migration collapses `evidencePath` into `documentPaths[0]`. If evidencePath is
null, `documentPaths = []`. Reads that dereference `evidencePath` (grep at
migration time) must switch to `documentPaths[0] ?? null`. UI unchanged.

### 8.6 `forms-engine.service.ts` writes into all three today
The forms engine at lines 1011, 1031, 1101 issues writes to
`safetyIncident`, `hazardObservation`, `correctiveAction`. Phase B/C slices
must update this single funnel to write through the shared `IssuesService`,
otherwise dual-write drift will grow every time a form is submitted.

### 8.7 SLICE 11 is the only irreversible slice
The contract migration cannot be undone. It ships only after Marco reads a
prod-stability report from Phase E covering ≥ one release cycle. This is the
whole reason SLICE 11 sits at the end alone.

### 8.8 Permission-alias window
SLICES 7–10 leave `cases.*`, `safety.*`, `forms.*` codes as aliases so any
external doc / runbook / role-config referencing them keeps working. SLICE 11
deletes them; SLICE 1 asks Marco to confirm no external system (CS runbook,
role import CSV) reads these codes.

## 9. PENDING-MARCO — shape-changing decisions before code slices start

### 9.1 Full consolidation vs SafetyIncident-kept-separate
**Question:** WHS audit obligations require that a safety incident's audit
trail is provably immutable and provably tied to a WHS-officer close-out.
Australian WHS regs (see sot/01:258-280, Marco as WHS officer sot/01:64,72)
put stronger duties on SafetyIncident than on Case or CorrectiveAction.

Two options:

**Option A (this plan's proposal): full consolidation with `IssueMovement`.**
Every mutating write logs an append-only movement row. `issues.close.safety`
permission is isHighRisk. Safety-specific fields live in `IssueSafety`.
Movement log = statutory audit trail.
- **Pro:** one engine, one code path, one comment thread model, one UI reuse.
- **Con:** any regression in `IssueMovement` write-through weakens the WHS
  audit trail for SafetyIncident. Marco has to trust the shared code path.

**Option B (partial consolidation): fold Case + CorrectiveAction; leave
SafetyIncident + HazardObservation separate.**
Cases and CorrectiveActions collapse into `Issue`. Safety keeps its own
tables and gets `SafetyIncidentMovement` / `HazardMovement` under the same
movement rule but in dedicated tables.
- **Pro:** WHS audit trail lives in a table only the safety service writes
  to; blast radius of any bug is narrower.
- **Con:** two engines instead of one — the whole motivation for the ruling
  weakens. Two UI code paths persist.

**Recommendation:** Option A, contingent on SLICE 6's backfill dry-run
producing a clean movement log for every existing SafetyIncident row (i.e.
we can prove the movement projection matches the current
`status`/`closedAt`/`closedById` state). If the dry-run diffs, escalate to
Option B before proceeding.

### 9.2 CaseType flattening vs nesting
See §3.2. Flattening trades enum-length for one fewer field. Marco's call.

### 9.3 CorrectiveAction gets a number
See §3.6. Introducing `CA-YYYY-NNN` changes the URL for existing rows'
detail pages (they will gain a shareable number). Marco confirms if that is
desired.

### 9.4 Unified `/issues` list
See §6. Marco's ruling did not include a unified UI. The plan preserves the
optionality (SLICE 10 optional route) but defers to Marco.

### 9.5 Permission code split for close-out authority
See §3.7. The proposal introduces `issues.close.safety` as a
kind-scoped high-risk close permission. Alternative: reuse `issues.manage`
and gate by kind in the service. Marco chooses.
