# Add the Claude Code GitHub Action workflow so @claude actually works

## Why this exists

On 2026-09-01 every write path into this repository was closed at once: the MCP server's
credential turned out to be read-only, local git could not release its own lock files through the
Cowork bridge, and the browser extension refused keystroke injection. Four PRs needed two-line
fixes and none could be applied by an agent. Marco applied them by hand.

The repository already has the machinery to avoid that. The **Claude GitHub App is installed**,
scoped to `GH-Mantova/ProjectOperations`, with *"Read and write access to actions, checks, code,
discussions, issues, pull requests, repository hooks, and workflows"*. It has been sitting there
doing nothing since it was installed, because nothing in `.github/workflows/` invokes it.

This slice adds that workflow. It gives the board an agent that can be reached by a PR comment and
that **can commit** - the exact capability that was missing.

## What to build

Create `.github/workflows/claude.yml` and nothing else. Base it on the interactive-mode example in
the official docs (https://code.claude.com/docs/en/github-actions), adapted to this repository's
conventions:

    name: Claude Code

    on:
      issue_comment:
        types: [created]
      pull_request_review_comment:
        types: [created]

    jobs:
      claude:
        if: contains(github.event.comment.body, '@claude')
        runs-on: ubuntu-latest
        timeout-minutes: 30
        permissions:
          contents: write
          pull-requests: write
          issues: write
          id-token: write
          actions: read
        steps:
          - uses: actions/checkout@v4.2.2
            with:
              fetch-depth: 1
          - uses: anthropics/claude-code-action@v1
            with:
              claude_code_oauth_token: ${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}
              claude_args: |
                --max-turns 15

Match this repo's existing workflow style: pin action versions exactly (ci.yml pins
`actions/checkout@v4.2.2`; the upstream example shows `@v6` - prefer the version already in use
here so the repo has one pin to maintain), declare `permissions:` explicitly, and write header
comments that explain WHY each non-obvious line is there. `ci.yml` is the model for comment
density - follow it.

## TRAP 1 - do NOT pass `github_token`. This one is repo-specific and it matters.

The docs are explicit: *"GitHub doesn't trigger workflows on commits made with the default
`GITHUB_TOKEN`. If you pass `github_token: ${{ secrets.GITHUB_TOKEN }}` to the Claude Code GitHub
Action, remove it so it authenticates as the Claude GitHub App."*

On this repository that is not a nicety, it is the whole point. **Every PR here is gated on CI**,
and `strict_required_status_checks_policy` is true. A commit that does not trigger `CI` leaves the
PR permanently pending its required checks - it can never merge, and the failure mode looks like a
hang rather than an error. Omit `github_token` entirely so the action authenticates as the Claude
GitHub App and its pushes fire `pull_request` events normally.

`done_when` asserts the absence of that key. Do not add it "for clarity".

## TRAP 2 - the secret does not exist yet, and only Marco can add it

The workflow is inert without an authentication secret. Marco must add **one** of:

- `CLAUDE_CODE_OAUTH_TOKEN` - authenticates against his Claude subscription, generated by running
  `claude setup-token` locally. No separate API bill; tied to his subscription.
- `ANTHROPIC_API_KEY` - a Claude API key from the Console, billed per token.

The YAML above uses the OAuth token. If Marco chooses the API key instead, that is a **one-line
swap** to `anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}`. Write the file with a comment
saying exactly that, so the alternative is one edit away and nobody has to re-read the docs.

**Do NOT attempt to create, read, or guess the secret.** Agents do not handle credentials. If the
secret is absent when this merges, the workflow simply never authenticates - it fails closed, which
is correct.

## TRAP 3 - who can make this run

The action runs two checks on whoever triggered it, and rejects the run if either fails:

- the triggering user must have **write access** to the repository;
- **bot actors are rejected** unless listed in `allowed_bots`.

Every actor on this board authenticates as the human user `GH-Mantova`, not as a bot, so both
checks pass as-is. **Do not add `allowed_bots`** - there is no bot here that needs it, and adding
one weakens the loop-prevention this check exists to provide.

## TRAP 4 - cost, and runaway runs

Each mention spends subscription or API tokens plus Actions minutes. Three guards, all in the YAML
above, all deliberate:

- `--max-turns 15` in `claude_args` caps iterations per run.
- `timeout-minutes: 30` on the job caps wall-clock.
- The `if:` condition keeps a runner from starting at all on comments that do not mention @claude.

Do not remove any of the three. Consider adding a `concurrency:` group keyed on the issue/PR number
so a burst of comments cannot start parallel runs - `ci.yml` already demonstrates the pattern.

## Do not do these things

- **Do not add a second workflow.** The code-review workflow from the docs is a separate decision
  with its own cost profile; this slice is the @claude responder only.
- **Do not modify `ci.yml`, `deploy.yml`, or either playwright workflow.**
- **Do not grant more permissions than the five listed.** In particular do not add
  `workflows: write` - an agent that can rewrite its own trigger conditions is a much larger
  decision than this slice is making.
- **Do not touch `.claude/settings.json` or `.claude/hooks/`.** Those guard local agent runs, not
  Actions runners; they are unrelated and changing them here would mix two concerns.
- **Do not add `docs/` files.** Everything a reader needs goes in the YAML's own header comments,
  which is this repo's established convention.

## Why this is Marco's to merge

`escalates: true` is set deliberately. This workflow lets anyone with write access to this
repository cause an AI agent to commit code to it, by writing a comment. That is a real expansion
of what can change this codebase without a human typing the change, and it should be a decision
somebody makes on purpose rather than one that arrives with a green tick.

It is also outside `^(tests|docs)/`, so `classifyPolicyFiles` routes it to Marco regardless - the
flag makes the intent explicit rather than incidental.

## Verify before you believe it

A green build proves the YAML parses. It does not prove the workflow works, and this file's whole
purpose is to work.

State plainly in the PR body that the end-to-end check - comment `@claude` on a PR and confirm a
workflow run starts - **cannot be performed until the secret exists**, and that it is Marco's to
run after merging. Do not claim the integration works. Claim only that the workflow is present,
parses, and is wired to the documented inputs.
